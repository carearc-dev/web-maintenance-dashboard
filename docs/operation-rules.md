# 社内Webサイト保守管理システム 運用ルール

## 1. 目的

この運用ルールは、弊社が管理するWebサイトの状態、契約、環境、認証情報、保守履歴を正確に保ち、誰が見ても現在の状況を判断できる状態を維持するためのものです。

本システムは、単なるログイン情報の保管場所ではありません。以下を一元管理する業務基盤として運用します。

- どのサイトを管理しているか
- 誰が担当しているか
- どの環境で動いているか
- どの保守対応が必要か
- いつ、誰が、何を対応したか
- 認証情報を誰が閲覧・利用したか

## 2. 基本方針

### 最新情報を正とする

サイト情報、サーバー情報、CMS情報、認証情報、担当者、契約内容は、このシステムに登録されている内容を社内の正とします。

スプレッドシート、チャット、メール、個人メモに情報が残っている場合でも、保守業務で使う情報は本システムへ転記・更新します。

### 作業したら必ず記録する

小さな作業でも、保守履歴に記録します。

例:

- WordPress本体更新
- プラグイン更新
- テーマ更新
- フォーム送信テスト
- 表示確認
- SSL確認
- バックアップ確認
- サーバー設定変更
- DNS変更
- リダイレクト設定
- 不具合調査

### 秘密情報をチャットやドキュメントに残さない

ログインID、パスワード、Basic認証、FTP、SSH、DB、APIキーなどは、原則として本システムの認証情報管理に登録します。

Slack、Chatwork、LINE、メール、Google Docs、スプレッドシートへ平文で残さないようにします。

## 3. 利用者ロール

| ロール | 主な役割 |
| --- | --- |
| 管理者 | 基本全ての業務が可能。ユーザー管理、権限管理、認証情報管理、監査ログ確認を行う |
| スタッフ | サイト情報の追加・修正、更新作業記録の入力、更新作業記録の削除を行う |
| エンジニア | 割り当てられたサイトの更新作業記録の入力、更新作業記録の削除を行う |

## 4. 基本操作方法

### ログイン

1. ログイン画面を開く
2. メールアドレスとパスワードを入力する
3. ログイン後、Dashboardを確認する

ログインできない場合は、管理者へ連絡します。パスワードをチャット上で共有しないでください。

### Dashboardを見る

Dashboardでは、管理サイト全体の状態を確認します。

確認する項目:

- 管理サイト数
- 正常サイト数
- 要確認サイト数
- 更新ありサイト数
- 障害サイト数
- 対応が必要なサイト
- SSLやドメイン期限に関するアラート

「要確認」「更新あり」「障害」が表示されている場合は、該当サイトの詳細画面を開き、内容を確認します。

### サイトを検索する

1. 左メニューの `Sites` を開く
2. 検索欄にサイト名、企業名、URL、担当者名のいずれかを入力する
3. 必要に応じてサイト種別やステータスで絞り込む
4. 対象サイトの行をクリックして詳細を開く

### サイト詳細を確認する

サイト詳細では、タブごとに情報を確認します。

| タブ | 確認内容 |
| --- | --- |
| 概要 | 企業名、サイトURL、担当者、契約内容、連携方法 |
| 環境情報 | サーバー、ドメイン、SSL、PHP、バックアップ |
| WordPress | WordPressバージョン、テーマ、プラグイン更新状況 |
| 保守情報 | 月次確認項目や要対応項目 |
| 認証情報 | 管理画面、サーバー、FTP、Basic認証など |
| 保守履歴 | 過去の作業内容 |
| メモ | 顧客別の注意事項 |

保守管理スプレッドシートがあるプロジェクトは、概要欄の `保守管理シート` から該当シートを開けます。まだシートがないプロジェクトは `準備中` と表示します。

### サイト情報を更新する

サイト情報に変更があった場合は、管理者または権限を持つ担当者が更新します。

更新が必要な例:

- 担当者が変わった
- サーバー会社が変わった
- ドメイン管理会社が変わった
- 契約内容が変わった
- 請求方法が変わった
- WordPressやPHPのバージョンが変わった
- SSLやドメインの期限が分かった

更新後は、必要に応じて保守履歴にも「情報更新」として記録します。

PHPバージョンは、公開ページのHTTPヘッダーから自動取得できる場合があります。ただし多くのサイトではセキュリティ上PHPバージョンを公開していないため、自動取得不可の場合はWordPress管理画面、サーバー管理画面、またはphpinfo等の安全な確認方法で担当者が確認します。

### 作業完了内容を登録する

1. 対象サイトの詳細画面を開く
2. `保守履歴` タブを開く
3. 作業日、作業カテゴリ、作業内容、確認したページ、フォーム送信テスト結果、作業時間を入力する
4. WordPress本体・プラグイン・テーマなどの更新がある場合は、対応前・対応後のバージョンを入力する
5. 未対応事項や追加確認が必要な内容があれば備考に入力する
6. `完了` ボタンを押す
7. 入力内容が `Maintenance` の保守履歴横断画面に記録される

作業内容は、あとから別の人が見ても分かる粒度で記録します。

既存の保守管理スプレッドシートがある場合も、作業完了内容はこのアプリ内へ登録します。過去履歴の参照や既存運用との照合が必要な場合は、サイト詳細の `保守管理シート` からスプレッドシートを開いて確認します。

### スポット対応プロジェクト

スポット対応のプロジェクトは、対応エンジニアを固定で設定せず、担当者は「未定」として管理します。

作業が発生した場合は、管理者またはスタッフが内容を確認し、必要に応じて作業・記録を行います。外部のエンジニアさんへ依頼が必要な場合は、都度、作業範囲と見積り要否を確認してから進めます。

担当者が「未定」のプロジェクトは、管理者またはスタッフのみ操作できます。エンジニア権限では、作業記録の入力・削除などの操作はできないようにします。

### 認証情報を確認する

1. 対象サイトの詳細画面を開く
2. `認証情報` タブを開く
3. 必要な認証情報だけを表示する
4. 作業が終わったら、画面を開いたまま離席しない

認証情報の表示・コピーは監査ログに記録されます。必要な作業目的がある場合のみ利用してください。

### アラートを確認する

1. 左メニューの `Alerts` を開く
2. アラートの内容と対象サイトを確認する
3. 対応が必要な場合は担当者へ共有する
4. 対応後、保守履歴を登録する
5. ステータスを更新する

### 操作ログを確認する

管理者は `Activity Logs` から以下を確認します。

- 誰がログインしたか
- 誰が認証情報を表示・コピーしたか
- 誰がサイト情報を変更したか
- 誰がユーザーや権限を変更したか

不審な操作があった場合は、該当ユーザーの権限を一時停止し、関係者へ確認します。

### Usersで権限を管理する

`Users` 画面でユーザー追加、権限変更、権限不要への切り替え、権限の再有効化を行います。

この画面を操作できるのは、管理者とスタッフのみです。

権限不要にしたユーザーは、必要に応じて同じ画面から権限を戻せます。

GitHub Pagesで公開する静的プレビューでは、管理者・スタッフ・エンジニアごとの簡易パスワードでログインし、画面上の操作を制御します。30分操作がない場合は自動ロックされ、ログイン失敗が5回続いた場合は10分間一時ロックされます。

外部攻撃への対策として、CSP、referrer制御、noindex、プレビューパスワードのハッシュ照合、ログイン連打防止、失敗時の遅延、ハニーポット項目、入力値のエスケープを入れています。

ただし、これは社内確認用の簡易制御であり、本物の認証・認可ではありません。HTMLとJavaScriptは閲覧者が確認できるため、実パスワードや顧客の秘密情報は置かないでください。

### Maintenanceで作業記録を編集・削除する

`Maintenance` 画面では、登録済みの作業記録を確認できます。

作業内容に誤りや追記がある場合は、編集ボタンから以下の詳細を修正できます。

- 作業日
- 対象サイト
- 作業カテゴリ
- 作業内容
- 確認したページ
- フォーム送信テスト結果
- 作業担当者
- 作業時間

重複登録や誤登録の場合は削除できます。ただし、実運用では削除操作も監査ログに残します。

## 5. サイト登録ルール

新しい保守対象サイトが発生した場合、管理者または担当ディレクターがサイトを登録します。

### 必須登録項目

- 企業名
- サイト名
- サイトURL
- サイト種別
- ステータス
- 担当ディレクター
- 担当エンジニア
- 保守開始日
- 契約内容
- 連絡方法
- 請求方法

### 可能な限り登録する項目

- 管理画面URL
- 保守管理シートURL
- サーバー会社
- サーバープラン
- PHPバージョン
- CMS
- WordPressバージョン
- テーマ名
- ドメイン管理会社
- SSL有効期限
- ドメイン有効期限
- DNS管理先
- CDN / WAF
- 管理画面URL
- バックアップ有無
- バックアップ頻度

### 登録時の注意

- 実在するパスワードを備考欄やメモ欄に書かない
- 認証情報は必ず認証情報タブへ登録する
- エンジニアさんには必要なサイトだけを割り当てる
- 他社サイトが見えないよう、割当後に権限を確認する

## 6. ステータス運用

| ステータス | 意味 | 使用例 |
| --- | --- | --- |
| 正常 | 現時点で対応不要 | 定期確認済み、期限問題なし |
| 要確認 | 情報不足または確認待ち | SSL期限未入力、担当未定、仕様確認中 |
| 更新あり | CMSやプラグイン更新が必要 | WordPress本体更新、プラグイン更新 |
| 障害 | サイト停止や重大不具合 | 500エラー、フォーム送信不可、表示崩れ |
| 保守停止 | 保守契約終了または一時停止 | 契約終了、顧客都合で停止中 |

### ステータス変更ルール

- 作業が必要な状態を見つけたら、ステータスを「要確認」または「更新あり」に変更する
- サイト停止や重大不具合は「障害」に変更する
- 対応完了後は保守履歴を登録し、必要に応じて「正常」へ戻す
- 保守終了サイトは削除せず「保守停止」にする

### 自動判定で確認する項目

新規サイト作成時、または定期監視時に、システムが公開URLを確認してステータスを自動判定します。

自動判定の対象:

- サイトURLにアクセスできるか
- HTTPステータスが `200 / 301 / 302 / 401 / 403 / 404 / 500 / timeout` のどれか
- 応答時間が極端に遅くないか
- HTTPSサイトのSSL証明書が有効か
- SSL証明書の期限が30日以内ではないか
- SSL証明書が期限切れではないか
- HTTPからHTTPSへリダイレクトされるか
- 公開ヘッダーからPHPバージョンが取得できるか

自動判定の例:

| 確認結果 | 自動ステータス |
| --- | --- |
| HTTP 200、SSL正常 | 正常 |
| HTTP 301 / 302、リダイレクト先が正常 | 正常 |
| HTTP 401 / 403 | 要確認 |
| HTTP 404 | 要確認 |
| HTTP 500 | 障害 |
| タイムアウト | 障害 |
| SSL期限30日以内 | 要確認 |
| SSL期限切れ | 障害 |

### 人が随時確認する項目

以下はシステムだけでは正確に判断できないため、担当者またはエンジニアさんによる確認が必要です。

- 契約内容に対して作業範囲が適切か
- 追加見積りが必要な作業か
- 顧客確認が必要な変更か
- 細かな表示崩れがないか
- フォーム送信後の業務フローが正しいか
- WordPress管理画面内のプラグイン更新可否
- 公開ページから取得できないPHPバージョン
- 更新によるデザインや機能への影響
- 顧客側で管理しているサーバー、ドメイン、メールの契約状態
- 請求対象になる作業時間か

自動判定は一次チェックとして扱い、判断が難しい内容は `要確認` として残し、担当者が確認します。

## 7. 保守履歴の記録ルール

保守作業を行ったら、作業当日中に保守履歴を登録します。

### 必須項目

- 作業日
- 作業担当者
- 作業カテゴリ
- 作業内容
- 作業時間

### 該当する場合に記録する項目

- 対応前バージョン
- 対応後バージョン
- 確認したページ
- フォーム送信テスト結果
- 備考

### 記入例

```text
作業日: 2026/09/01
担当: 山田
カテゴリ: WordPressプラグイン更新
作業内容: Contact Form 7を5.9から6.0へ更新。フォーム送信テスト、主要ページ表示確認済み。
作業時間: 20分
対応前: Contact Form 7 5.9
対応後: Contact Form 7 6.0
備考: 問い合わせフォーム、完了メールともに正常。
確認ページ: お問い合わせページ、送信完了ページ、トップページ
フォーム送信テスト: 正常に送信できることを確認
```

### 悪い記入例

```text
作業内容: 対応しました
```

何を行ったか、どこまで確認したかが分からないため不可です。

## 8. 認証情報の運用ルール

### 登録対象

- WordPress
- Shopify
- サーバー管理画面
- サーバーパスワード
- FTP / SFTP
- SSH
- データベース
- Google Analytics
- Google Search Console
- ドメイン管理
- Basic認証
- テスト環境
- その他外部サービス

### 登録ルール

- パスワードは認証情報タブにのみ登録する
- メモ欄にパスワードを書かない
- 退職者、外部パートナー変更、顧客担当者変更があった場合は認証情報を見直す
- 使用しなくなった認証情報は削除ではなく無効化・備考追記を基本とする
- サーバーパスワードがあるプロジェクトは、認証情報として登録し、変更日時を必ず記録する
- サーバーパスワードがないプロジェクトは、画面上で「登録なし」と分かる状態にする

### 閲覧ルール

- 必要な作業がある場合のみ表示する
- 表示・コピー操作は監査ログに残る前提で扱う
- エンジニアさんには必要な認証情報のみ閲覧許可する
- 顧客や無関係なサイトの認証情報は絶対に共有しない

## 9. エンジニアさんへの作業依頼・共有ルール

エンジニアさんは、弊社の保守品質を一緒に支えてくださる重要な協力者です。

依頼時は一方的な指示にならないよう、背景、目的、確認範囲、判断が必要な点を丁寧に共有します。作業の進め方について専門的な懸念やより良い方法がある場合は、遠慮なく提案いただける関係を前提にします。

### 依頼時の基本姿勢

- 作業の背景と目的を添えてお願いする
- 期限や優先度を明確にする
- 本番作業かテスト作業かを明確にする
- 判断に迷う点は事前相談をお願いする
- 作業後の確認内容を具体的に共有する
- 追加工数が発生しそうな場合は、事前に相談いただく
- 完了後、このアプリ内で作業内容をご記録いただくようお願いする

### 作業前に確認すること

- 対象サイト名
- 本番環境かテスト環境か
- 作業範囲
- 作業期限
- バックアップ要否
- 顧客確認が必要か
- 作業後に確認すべきページ
- フォーム送信テストの要否
- 確認していただきたいページ

### 作業中にお願いしたいこと

- 本番環境を触る前に必要に応じてバックアップを取得する
- 顧客データ、注文データ、問い合わせデータを不用意に変更しない
- WordPress更新時は本体、テーマ、プラグインの互換性を確認する
- PHPバージョン変更時は管理画面、フォーム、主要ページを確認する
- Basic認証やログイン情報をチャットに貼らない
- 不明点がある場合は推測で進めず、担当者へ確認いただく
- 想定より作業範囲が広がる場合は、着手前に共有いただく

### 作業後にお願いしたいこと

- 作業内容を保守履歴へ登録いただく
- 登録場所は、対象サイト詳細の `保守履歴` タブにある「作業完了内容を入力」フォーム
- 更新前後のバージョンを記録いただく
- 表示確認したページを記録いただく
- フォーム送信テスト結果を記録いただく
- エラーや未対応事項があれば備考へ残していただく
- 入力後、`完了` ボタンを押して記録いただく
- ステータス変更が必要そうな場合は、担当者へ共有いただく

## 10. ディレクター・運用担当向けルール

### 依頼を受けたとき

1. 対象サイトを検索する
2. 契約範囲内の作業か確認する
3. 担当エンジニアを確認する
4. 必要な認証情報の閲覧権限を確認する
5. 作業内容、期限、確認範囲をエンジニアさんへ丁寧に共有する

### 作業完了後

1. 保守履歴が登録されているか確認する
2. 顧客へ報告が必要な内容を確認する
3. 請求対象の追加作業がある場合は記録する
4. ステータスを更新する

## 11. 定期確認ルール

### 週次確認

- 要確認サイト
- 更新ありサイト
- 障害サイト
- 担当者未定サイト
- 認証情報が未整理のサイト

### 月次確認

- WordPress本体更新
- プラグイン更新
- テーマ更新
- PHPバージョン
- SSL期限
- ドメイン期限
- バックアップ状況
- フォーム送信テスト
- Search Console
- アクセス解析

### 契約・請求確認

- 月額保守時間を超えていないか
- 追加見積り対象の作業がないか
- 請求方法が最新か
- 請求先担当者が最新か

## 12. 障害発生時の運用

サイト停止、HTTP 500、フォーム送信不可、重大な表示崩れなどを確認した場合は、以下の手順で対応します。

1. サイトステータスを「障害」に変更する
2. 発生日時と確認内容を保守履歴へ記録する
3. 担当者へ即時連携する
4. 顧客への報告要否を確認する
5. 復旧作業を実施する
6. 復旧後、原因・対応内容・再発防止策を保守履歴へ記録する
7. ステータスを「正常」または「要確認」へ戻す

## 13. 権限管理ルール

### エンジニアさん

- 割り当てられたサイトのみ閲覧可能にする
- 顧客名、他サイト情報、認証情報の横断閲覧は許可しない
- 認証情報閲覧は必要最小限にする
- 作業終了後、継続不要であれば閲覧権限を外す
- 権限制限は不信ではなく、顧客情報保護と双方の安全のために行う

### 社内スタッフ

- 担当業務に必要なサイトのみ閲覧可能にする
- 認証情報の閲覧可否は管理者が判断する

### 管理者

- ユーザー追加・削除・権限変更を行う
- 監査ログを定期的に確認する
- 退職者や契約終了パートナーの権限を速やかに削除する

## 14. 入力ルール

### 表記ルール

- 企業名は正式名称で登録する
- サイト名は社内で呼びやすい名称にする
- URLは `https://` または `http://` から登録する
- 日付は `YYYY/MM/DD` 形式で統一する
- 未定の場合は空欄ではなく「未定」と記載する
- 不明な場合は「要確認」と記載し、サイトステータスも「要確認」にする

### メモ欄の使い方

メモ欄には、作業判断に必要な補足情報を記載します。

記載してよいもの:

- 顧客ごとの注意事項
- 連携時のルール
- 追加見積りが必要な条件
- 過去のトラブル傾向
- 作業前に確認すべき事項

記載してはいけないもの:

- パスワード
- APIキー
- Basic認証情報
- 秘密鍵
- 個人情報を含む不要なメモ
